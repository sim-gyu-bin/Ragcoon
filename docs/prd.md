# RAGcoon 제품 요구사항 (PRD)

**상태: 구현 전 초안.** [README](../README.md)의 기술 선택과 로드맵을 기준으로, 각 단계에서 사용자가 할 수 있어야 하는 일과 완료 조건을 정의한다. 아래 기준은 테스트 결과가 아니다.

## 1. 대상과 목표

주 사용자는 자신이 올린 문서로 RAG를 공부하는 개인 개발자다. 사용자는 질문에 대한 답뿐 아니라 **무엇을 검색했고 그 근거로 왜 그런 답이 나왔는지** 확인할 수 있어야 한다. 답이 틀리면 검색이 필요한 문단을 놓쳤는지, 문단은 찾았지만 답변 생성이 잘못됐는지 나눠 살펴볼 수 있어야 한다.

첫 제품 목표는 **한국어 Markdown 문서 하나를 올리고, 질문에 답한 원문 위치까지 확인하는 것**이다. PDF, 스트리밍, 대화 기록은 이 흐름을 확인한 뒤 같은 RAG 단계에서 추가한다. 다중 사용자 협업, 공개 문서 공유, OCR, 로컬 모델 서빙은 초기 범위에서 제외한다.

## 2. 핵심 사용 시나리오

사용자가 운영 안내서를 올린 뒤 “백업은 언제 실행돼?”라고 묻는다. 검색 결과에는 안내서의 백업 일정 문단이 나타난다. 답변의 출처를 선택하면 사용자는 같은 문서의 해당 원문을 읽을 수 있다. 이어서 문서에 없는 보관 기간을 물으면, 시스템은 일정을 보관 기간으로 오인하거나 숫자를 지어내지 않고 확인할 근거가 부족하다고 알린다.

## 3. 기능 요구사항과 인수 기준

| ID | 요구사항 | 완료 조건 |
|---|---|---|
| F1 | React 화면에서 FastAPI 연결 상태를 확인한다. | 로컬 Compose 환경에서 API가 응답하면 정상으로 보이고, 연결이 끊기면 성공 상태와 구분된다. |
| D1 | Markdown과 텍스트 추출이 가능한 PDF를 등록하고 목록에서 색인 상태를 확인한다. | 업로드 성공과 검색 준비 완료를 구분한다. 텍스트가 없는 PDF 또는 임베딩 실패는 원문을 노출하지 않는 오류로 표시하고 부분 색인 결과를 검색에 쓰지 않는다. |
| D2 | 등록한 문서를 삭제한다. | 삭제 완료 후 목록에서 사라지고 해당 문서의 청크가 새 검색에 포함되지 않는다. 다른 문서의 검색 결과는 유지된다. |
| R1 | 검색 기본값은 하이브리드(RRF)이며 희소(SQLite FTS5의 BM25)·밀집(ChromaDB)을 선택할 수 있다. | 첫 화면과 API의 `mode` 생략은 `hybrid`, 명시한 `sparse`·`dense`는 각각 해당 검색만 실행한다. 채팅 모델 없이 순위·원문·출처 위치를 확인한다. 희소 질의는 임베딩 API를 호출하지 않고 하이브리드는 청크 ID 중복을 제거한다. |
| R2 | 검색한 근거를 사용해 질문에 답한다. | 답변 출처에서 실제 검색된 원문을 열 수 있다. 근거가 없는 평가 질문에는 문서에서 확인할 수 없다고 표시하고 가짜 출처를 만들지 않는다. |
| C1 | 답변을 생성 중에 읽고 이전 대화를 다시 본다. | 응답이 완료되기 전부터 내용이 표시된다. 새로고침 후 세션별 메시지를 다시 볼 수 있고, 스트리밍 실패를 완료된 답변으로 표시하지 않는다. |
| A1 | 기본 RAG와 LangGraph Agent의 실행 과정을 비교한다. | 동일 질문에서 검색·판정·분기·도구 호출 중 실제 수행한 단계가 표시된다. 근거가 부족하면 정해진 상한 안에서 재검색하고, 상한에 도달하면 부족한 상태로 종료한다. |
| E1 | 검색 품질과 답변 품질을 분리해 평가한다. | 같은 문서·질문 집합으로 변경 전후를 비교한다. 추적을 켠 실험에서는 LangSmith에서 해당 실행 단계를 확인하고, 꺼 둬도 기본 질의응답은 가능하다. |

## 4. 데이터·모델·안전 경계

- **임베딩은 OpenAI `text-embedding-3-small`로 고정한다.** 문서 청크와 질문에 같은 모델을 쓴다. 답변 생성 모델은 별도이며 아직 미정이다. 임베딩 모델 교체 시 기존 벡터와 섞지 않고 문서를 다시 색인해야 한다.
- 세 모드는 동일한 청크와 출처를 사용한다. 두 색인이 모두 완성된 문서만 노출하고, 삭제된 문서는 어느 모드에도 나타나지 않아야 한다. 답변 생성에는 선택한 모드의 검색 근거를 전달한다.
- SQLite는 문서 상태·원문·청크별 줄 범위와 단어 색인을, ChromaDB는 청크 ID별 벡터와 문서 ID를 보관한다. 문서 이름이 같아도 서로의 출처나 삭제 대상이 뒤섞이지 않아야 한다. 채팅 세션과 메시지는 L04에서 SQLite에 저장한다.
- 외부 전송이 가능한 자료만 사용한다. 임베딩에는 청크와 질문이, 외부 답변 생성에는 질문과 검색된 근거가 전달된다. API 키는 백엔드에서만 읽는다. 원문·키·대화를 로그나 오류 응답에 기록하지 않는다.
- 검색된 문서 속 지시는 참고 텍스트이지 도구 실행 권한이 아니다. LangSmith 추적은 기본 비활성화하고 전송 필드와 비용을 확인한 실험에서만 켠다. 자동 테스트는 유료 API나 운영 데이터 없이 수행한다.

## 5. 단계별 검증과 출시 조건

1. **기반:** F1. 개발자가 화면과 API 응답을 직접 대조한다.
2. **RAG:** Markdown으로 D1 → R1 → R2를 먼저 연결한다. 이후 PDF·삭제·스트리밍·기록까지 D1~D2, R1~R2, C1을 확인한다. Agent 없이 동작하는 이 버전을 비교 기준으로 남긴다.
3. **Agent:** A1. 기본 검색이 놓친 실제 예시로 조건부 재검색을 검증한다. 재검색 성공뿐 아니라 끝까지 근거를 못 찾는 경우도 확인한다.
4. **평가:** E1. 바꿔 표현한 질문, 정확한 용어·식별자를 찾는 질문, 근거 없는 질문을 포함해 한국어 질문 약 10개를 준비한다. 같은 문서·질문으로 세 모드를 비교한다. 답이 있는 질문은 모드별 상위 3개에 정답 문단이 포함된 비율을, 답변은 인용의 정확성과 근거 부족 응답을 기록한다. 하이브리드가 항상 우수하다고 가정하지 않는다.
5. **운영:** 목표 환경은 OCI 오사카 Ampere A1(2 OCPU, 12GB RAM), Ubuntu 24.04 ARM64다. GitHub Actions 배포 후 Caddy HTTPS를 통한 실제 질의, 컨테이너 재생성 후 데이터 유지, 격리된 위치에서의 백업 복구, 상태·오류 확인을 검증한다. 외부 접근 통제와 API 비용 한도가 결정되기 전에는 공개 서비스를 출시하지 않는다.

## 6. 구현 전에 남은 결정

| 결정 시점 | 미정 항목 | 판단 기준 |
|---|---|---|
| 문서 업로드 구현 전 | 파일 크기·페이지 제한, 원본 보관 기간 | 대상 VM 자원, 재색인 가능 여부, 외부 전송 비용 |
| 첫 검색 실험 | 청크 크기·겹침·검색 개수 | 한국어 질문의 기대 문단 포함 여부와 출처 가독성 |
| 답변 생성 연결 전 | 채팅 모델과 호출 예산 | 같은 근거에 대한 답변 정확성, 응답 시간, 비용 |
| Agent 구현 전 | 재검색 상한과 허용 도구 | 기본 RAG의 실패 사례, 무한 반복 방지, 추가 호출 비용 |
| 외부 배포 전 | 접근 통제 방식, 사용 한도, 백업·복구 주기 | 개인용 접근 범위, 비용 노출, 허용 가능한 데이터 손실 |
