# 같은 질문으로 배우는 희소·밀집·하이브리드 검색

**검색 방식은 세 가지다. ‘순위’는 네 번째 방식이 아니라, 각 방식이 찾아낸 문단을 보여주는 순서다.** RAG에서 검색은 답을 쓰는 일이 아니다. 답변의 근거가 될 문단(청크)을 고르는 일이다.

## 질문 하나, 문단 두 개

질문은 **“백업은 언제 해?”**이고, 문서에 다음 두 문단이 있다고 하자.

- **A:** “백업 담당자는 인프라팀이다.”
- **B:** “데이터 복사본은 매일 새벽 3시에 생성한다.”

사람은 B를 답의 근거로 고를 수 있다. 그런데 질문과 같은 단어인 ‘백업’이 들어간 쪽은 A다. 이 차이가 두 검색 방식을 공부하는 출발점이다. 아래는 원리를 설명하는 예시이지 실제 모델의 측정 결과가 아니다.

### 희소 검색: 어떤 단어가 겹치는가?

문서 전체의 어휘 중 한 문단에 등장하는 단어는 일부뿐이다. 단어별로 점수를 표현하면 대부분이 비어 있어 ‘희소’라고 한다. RAGcoon에서는 SQLite의 전문 검색 기능인 FTS5로 검색어와 일치하는 청크를 찾는다.

예시에서는 ‘백업’이 같은 검색 단위로 분리되면 A를 찾기 쉽지만, ‘복사본’만 쓰인 B를 놓칠 수 있다. 따라서 한국어 조사나 `OPENAI_API_KEY` 같은 식별자를 어떻게 나누는지도 실험 대상이다. 질의할 때 임베딩 API를 호출하지 않는다.

#### BM25: 일치하는 문단 중 무엇을 먼저 보여줄까?

**BM25(Best Matching 25)는 정보 검색 분야의 순위 알고리즘**이다. 희소 검색이 ‘단어로 찾는다’는 접근법이라면, BM25는 ‘찾은 문단을 어떤 순서로 보여줄까?’에 답하는 계산법이다. LLM이나 임베딩 모델은 필요 없다.

예를 들어 `백업 주기`를 검색할 때 BM25는 다음 단서를 함께 본다.

- **단어의 희귀도:** `백업`은 거의 모든 문단에 있고 `주기`는 몇 문단에만 있다면, `주기`의 일치가 문단을 구별하는 데 더 유용하다.
- **등장 횟수:** 한 문단에서 검색어가 반복되면 관련성의 단서가 되지만, 반복할수록 추가 효과는 줄어든다. 열 번 썼다고 열 배의 점수를 받지는 않는다.
- **문단 길이:** 긴 문단은 단어를 포함할 기회도 많다. 그래서 단순 횟수만 세지 않고 전체 문단의 평균 길이를 기준으로 보정한다.

이 점수는 **단어가 얼마나 잘 맞는지**를 나타내지, 문단이 정답일 확률을 뜻하지 않는다. “백업 주기는 아직 정하지 않았다”도 검색어에는 잘 맞는다.

#### RAGcoon에서는 BM25를 직접 구현할까?

아니다. **FTS5를 지원하는 SQLite에는 `bm25()`가 내장돼 있다.** 일반 테이블에 적용하는 함수가 아니라, FTS5 가상 테이블에서 검색 결과의 순위를 매길 때 쓰는 함수다. 예를 들어 `chunks_fts`가 청크를 색인한 FTS5 테이블이라면, `?`에 검색어를 바인딩해 다음처럼 조회한다.

```sql
SELECT rowid AS chunk_id
FROM chunks_fts
WHERE chunks_fts MATCH ?
ORDER BY bm25(chunks_fts) ASC
LIMIT 3;
```

`MATCH`는 어떤 청크가 검색어와 일치하는지 찾고, `bm25()`는 그 안에서 순서를 정한다. SQLite FTS5에서는 **값이 작을수록 더 좋은 일치**이므로 오름차순(`ASC`)으로 정렬한다.

**SQLite를 쓰는 이점**은 문서 목록과 채팅 기록을 보관할 DB에서 단어 검색까지 해결한다는 점이다. 별도 키워드 검색 서버나 자체 BM25 구현이 필요 없다. 다만 문서를 삭제하거나 다시 색인할 때는 백엔드가 SQLite와 ChromaDB 양쪽을 관리해야 한다. 같은 청크 ID는 두 결과를 연결하는 열쇠이지, 두 색인을 자동으로 동기화하는 장치는 아니다.

### 밀집 검색: 표현이 달라도 의미가 가까운가?

`text-embedding-3-small`로 문단을 여러 숫자로 이루어진 벡터로 바꿔 ChromaDB에 색인한다. 질문도 같은 모델로 변환한 뒤 가까운 문단을 찾는다. 단어마다 자리를 하나씩 두는 대신, 여러 수치에 걸쳐 의미를 표현해서 ‘밀집’이라고 한다.

‘백업’과 ‘복사본’의 관련성 덕분에 B가 후보가 될 수 있다. 하지만 A 역시 백업 이야기다. **의미가 비슷하다는 점수가 높아도 질문에 답하는 문단이라는 보장은 없다.**

### 하이브리드 검색: 두 목록을 어떻게 합치는가?

같은 질문으로 두 검색을 실행하고, 공통 청크 ID로 후보를 모은다. BM25 점수와 벡터 유사도는 척도가 달라 그대로 더하지 않는다. RAGcoon의 설계는 각 목록에서 **몇 위였는지**만 사용하는 RRF(Reciprocal Rank Fusion)다.

예를 들어 A가 희소 1위·밀집 2위이고 B는 밀집 1위에만 있다면, A는 두 목록에서 점수를 받고 B는 한 목록에서만 받는다. 한 목록의 기여도는 `1 / (k + 순위)`다. 순위는 1부터 시작하고 `k`는 순위 차이의 영향을 조절하는 양의 상수다. 이 예에서는 A가 최종 1위다. **두 방식을 합쳐도 정답 B가 반드시 맨 위로 오는 것은 아니다.** 그래서 점수만 보지 않고 상위 문단의 원문을 확인한다.

## RAGcoon에서 비교하는 법 (구현 계획)

검색 화면의 기본값은 **하이브리드**다. 옵션을 바꾸지 않거나 API에서 `mode`를 생략하면 `hybrid`로 검색한다. 단어 일치만 보고 싶으면 `sparse`, 의미 유사도만 보고 싶으면 `dense`를 선택한다. 하이브리드도 밀집 검색을 포함하므로 질문 임베딩 호출 비용이 발생할 수 있다.

같은 문서와 질문을 고정하고 모드만 바꿔 보자. 각 모드의 상위 세 문단에 B가 있는지, 몇 위인지, 원문이 실제로 질문에 답하는지 확인한다. 그다음 질문을 ‘복사본 생성 시각은?’으로 바꾸면, 같은 근거를 찾으면서도 단어 선택이 순위에 주는 영향을 관찰할 수 있다.
