# RAGcoon 단계별 작업 플랜

기준: [제품 요구사항](prd.md) · [프로젝트 개요](../README.md). 아래 체크박스는 실행 순서이며 완료 보고가 아니다.

## 진행 방식

- **한 번에 체크박스 하나.** 사용자가 단계 번호를 지정하면 AI가 그 단계의 설계·구현·관련 검증까지 맡는다. 다음 번호로 자동 진행하지 않는다. 실패하면 해당 단계 안에서 원인을 좁히고, 검증되지 않은 항목은 체크하지 않는다.
- **사용자는 결과를 확인하고 질문한다.** 단계 끝에 AI가 직접 관찰한 결과, 사용자가 선택적으로 재현할 명령이나 화면 경로, 먼저 읽을 파일·함수와 선택 이유를 남긴다. 설명 요청만으로 구현을 바꾸지 않는다.
- **계정 작업도 AI가 조사한다.** 로그인·MFA·비밀 입력처럼 본인만 할 수 있는 동작과 비용·권한·외부 공개·운영 변경·삭제 승인은 사용자가 맡는다. 키나 비밀번호를 채팅으로 요청하지 않는다. 단계 착수는 커밋·푸시·배포 승인을 뜻하지 않는다.

## 1. 로컬 기반 — 브라우저의 요청이 서버까지 가는지 보기

L01~L02는 구성 요소를 따로 실행해 배우는 단계다. L03~L16의 로컬 통합 검증은 Docker Compose의 Caddy 주소로 접속한다. 호스트의 Vite 개발 서버나 FastAPI 직접 호출을 통합 검증으로 대신하지 않는다.

- [ ] **L01 · FastAPI 첫 응답.** `apps/api`에 uv 기반 앱과 `GET /api/health`를 만든다. **확인:** 로컬 HTTP 요청으로 상태 코드와 JSON을 본다. 이 단계에는 DB·Docker·API 키가 필요 없다.
- [ ] **L02 · React 연결 화면.** `apps/web`에 pnpm·Vite·TypeScript 화면을 만들고 health API를 연결한다. **확인:** 브라우저 Network 응답과 화면을 대조하고, 서버가 응답하지 않을 때 연결 실패가 표시되는지 본다.
- [ ] **L03 · Caddy를 통한 로컬 Compose 통합.** Caddy와 FastAPI를 컨테이너로 실행한다. Caddy는 React 빌드 파일을 직접 제공하고, 브라우저의 `/api/` 요청만 경로를 유지해 FastAPI로 전달한다. 호스트에는 Caddy 포트만 `127.0.0.1`에 바인딩하고 FastAPI 포트는 공개하지 않는다. **확인:** 같은 주소에서 `/`는 화면을, `/api/health`는 FastAPI의 JSON을 반환한다. FastAPI만 중단한 뒤 화면을 새로고침하면 React 화면은 열리고 API 연결 실패가 표시된다(F1).

## 2. 기본 RAG — 생성보다 검색을 먼저 확인하기

- [ ] **L04 · Markdown 등록과 목록.** 파일 제한과 보관 정책을 정하고 업로드 화면·SQLite 메타데이터를 연결한다. **확인:** 같은 이름의 두 문서가 별도 ID로 등록되고, 등록 직후에는 검색 준비 완료로 표시되지 않는다.
- [ ] **L05 · 청크와 출처.** Markdown을 나누고 문서 ID와 원문 구간을 보존한다. **확인:** 한국어 샘플에서 각 청크의 위치로 실제 원문을 찾을 수 있다. 아직 임베딩을 호출하지 않는다.
- [ ] **L06a · 밀집 색인.** `text-embedding-3-small`로 청크를 벡터화해 ChromaDB에 공통 청크 ID로 저장한다. 첫 유료 호출 전 샘플 문서와 호출 범위에 대한 승인을 받는다. **확인:** 저장된 벡터에서 원문 구간을 찾을 수 있다. 자동 테스트는 외부 호출 없이 격리한다.
- [ ] **L06b · 희소 색인.** 대상 컨테이너의 SQLite FTS5 지원을 확인하고 같은 청크 ID로 전문 색인을 만든다. **확인:** 두 색인이 모두 성공해야 문서가 검색 가능해지며 한쪽 색인이 실패한 문서는 노출되지 않는다.
- [ ] **L07a · 밀집 검색 화면.** 질문 임베딩으로 ChromaDB를 검색하고 순위·문서명·구간·원문을 표시한다. **확인:** 단어가 달라도 뜻이 비슷한 질문으로 기대 문단의 순위를 확인한다.
- [ ] **L07b · 희소 검색 모드.** 같은 화면에서 SQLite FTS5의 BM25 검색을 선택한다. 문서와 질문에 같은 토큰화 기준을 적용한다. **확인:** 한국어 용어와 `OPENAI_API_KEY` 같은 식별자로 검색해 원문을 확인하고, 질의 시 임베딩 API가 호출되지 않는지 본다.
- [ ] **L07c · 기본 하이브리드 검색.** 두 후보 목록을 청크 ID로 합쳐 RRF로 정렬한다. 화면 기본 선택과 API의 `mode` 생략은 `hybrid`로 맞추고 `sparse`·`dense`는 단독 검색 옵션으로 유지한다. **확인:** 같은 질문으로 생략과 명시적 `hybrid`가 같은 방식으로 처리되고 옵션 전환 시 지정한 검색만 실행되는지 본다. 양쪽에 나온 청크는 한 번만, 한쪽에만 나온 청크도 후보에 남는다(R1).
- [ ] **L08 · 출처가 있는 첫 답변.** 채팅 모델과 호출 예산을 정한 뒤 LangChain으로 검색 근거를 전달한다. **확인:** 답변의 출처를 눌러 정답 문단을 열고, 문서에 없는 질문에는 근거나 출처를 꾸미지 않는지 비교한다(R2). **여기서 첫 제품 목표를 시연한다.**
- [ ] **L09 · PDF.** 텍스트 PDF를 같은 색인 경로에 연결하고 페이지를 보존한다. **확인:** 인용 페이지와 원문이 맞고, 텍스트가 없는 PDF는 이유를 표시하며 검색에 노출되지 않는다(D1).
- [ ] **L10 · 문서 삭제.** 문서 ID 기준으로 두 색인과 저장 데이터를 정리한다. **확인:** 삭제를 승인받은 격리 샘플이 목록과 세 검색 모드에서 사라지고, 같은 이름의 다른 문서는 남는다(D2).
- [ ] **L11 · 응답 스트리밍.** 생성 중인 답변을 화면에 표시한다. **확인:** 완료 전부터 내용이 보이고 중간 연결 실패가 완료로 표시되지 않는다.
- [ ] **L12 · 대화 기록.** SQLite에 세션별 메시지와 응답 상태를 저장한다. **확인:** 새로고침 후 대화가 복원되고 다른 세션의 메시지가 섞이지 않는다(C1).

## 3. Agent·평가 — 로컬 완료 판정

- [ ] **L13 · 검색 방식별 기준선.** 한국어 질문 약 10개에 기대 원문 또는 ‘근거 없음’을 지정한다. 의미를 바꿔 표현한 질문과 정확한 용어·식별자 질문을 포함한다. **확인:** 같은 문서·질문으로 밀집·희소·하이브리드 각각의 상위 3개 정답 문단 포함률을 비교하고, 인용 정확성과 근거 부족 응답은 따로 기록한다.
- [ ] **L14 · 제한된 Agent.** 기본 검색 실패 예시를 골라 LangGraph 판정·조건부 재검색과 허용된 검색 도구를 연결한다. **확인:** 화면에 실제 실행한 단계만 나타나고, 재검색으로 근거를 찾은 경우와 상한까지 실패한 경우 모두 종료한다(A1).
- [ ] **L15 · 추적과 비교 평가.** 기본 RAG와 Agent를 동일 질문으로 비교한다. LangSmith는 전송 필드·비용 확인과 승인 후 합성 예제로만 켠다. **확인:** 추적에서 실제 호출 순서를 보고, 추적을 꺼도 질의응답이 동작한다(E1).
- [ ] **L16 · 로컬 완료 관문.** AI가 격리된 데이터로 Pytest·Vitest와 프론트 빌드를 실행한다. L03의 Caddy 주소로 접속해 등록 → 검색 → 인용 답변 → 기록 복원을 재현하고, 브라우저 Network에서 API 호출이 같은 주소의 `/api/` 경로를 사용하는지 확인한다. 컨테이너 재생성 후에도 같은 화면에서 문서와 검색 결과가 유지되는지 본다. **통과 조건:** F1~E1의 단계별 증거, 실행 명령, 외부 호출 여부를 제시하고 실패·미검증 항목이 없을 것. 사용자 확인 전에는 OCI 조사나 배포에 착수하지 않는다.

## 4. OCI — 조회와 변경을 분리하기

이 단계의 오사카 A1·2 OCPU·12GB·Ubuntu 24.04 ARM64는 **목표 사양**이다. 기존 VM의 존재, 무료 적용, 여유 용량을 가정하지 않는다.

- [ ] **O01 · 읽기 전용 실사.** 사용자가 허용한 컴퓨터 유즈 세션에서 AI가 OCI 콘솔을 직접 탐색한다. 리전·구획, 기존 VM과 사용 용도, shape·OS·스토리지, 네트워크·인바운드 규칙, 접속 경로, 표시된 한도·비용을 확인한다. 도메인·DNS·GitHub 배포 권한은 허용된 서비스 화면에서 필요한 범위만 본다. **산출물:** ‘관찰값 / 목표와 차이 / 확인 불가’ 표. 값 수집이나 스크린샷 작성을 사용자에게 맡기지 않는다. 권한·세션이 없으면 필요한 로그인 또는 접근 허용만 요청한다. 식별자·접속 정보·비밀은 저장소에 남기지 않는다.
- [ ] **O02 · 배포안 승인.** AI가 기존 VM 재사용 가능성, 신규 자원 필요 여부, 예상 비용·불확실성, 변경할 네트워크·DNS·권한, 개인용 접근 통제, 호출 한도, 백업·복구 순서를 제시한다. **완료 조건:** 사용자가 대상과 변경 범위를 확인한다. 비용이나 기존 서비스 영향이 불명확하면 자원을 만들지 않는다.
- [ ] **O03 · VM 준비.** 승인된 범위에서만 AI가 콘솔·터미널로 VM을 준비하고 접속·Docker·디스크·ARM64 이미지 호환성을 확인한다. **확인:** 대상 VM의 실제 아키텍처와 실행 결과를 보고한다. 한도 부족이나 과금 표시가 승인안과 다르면 대안만 제시하고 멈춘다.
- [ ] **O04 · 비공개 첫 기동.** 서버 측 비밀 주입과 영구 볼륨을 구성하고 외부 공개 전에 Compose를 기동한다. 로컬 DB를 운영으로 복사하지 않는다. **확인:** VM 내부에서 health와 합성 문서 검색이 동작하고 API·DB 포트가 의도치 않게 외부로 열리지 않는다.
- [ ] **O05 · HTTPS와 접근 제어.** 승인된 도메인·DNS·인바운드 변경으로 Caddy를 연결한다. **확인:** 허용된 사용자만 HTTPS로 업로드와 질의를 할 수 있고 미인증 직접 API 요청은 거절된다. 호출 한도와 외부 전송 설정도 확인한다.
- [ ] **O06 · GitHub Actions 배포.** private 저장소에서 검사·빌드와 승인 후 배포를 분리한다. **확인:** 검사 실패 시 배포되지 않고, 승인된 리비전 배포 후 HTTPS 화면과 API가 정상이다. 이미지 롤백과 데이터 복구는 별개로 다룬다.
- [ ] **O07 · 운영 인수.** 합의한 주기로 백업을 구성하고 별도 격리 위치에 복원한다. **확인:** 복원본의 문서·검색·대화가 일치하고 운영 데이터는 그대로다. AI가 상태·오류·비용 확인 위치와 장애 시 복구 절차를 정리하고 사용자는 결과를 확인한다.

**첫 요청 예시:** `L01만 진행해줘.` 이후에는 번호를 지정해 이어가거나, 다음 단계로 넘어가기 전에 방금 만든 코드에 대해 질문한다.
